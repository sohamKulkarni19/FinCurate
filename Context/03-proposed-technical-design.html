1. Design overview

The application is a local modular monolith: one Python project, one Streamlit process, one SQLite database, and a managed data directory. The domain calculation layer is deliberately independent of Streamlit and external providers.

UI layer

Renders pages and charts; converts user actions into application-service requests.

Application layer

Coordinates use cases such as refresh, explore, compare, screen, shortlist, and export.

Domain layer

Owns dates, eligibility rules, returns, risk metrics, statistics, and validation invariants.

Infrastructure layer

Implements source clients, snapshot storage, SQLite repositories, migrations, logging, and file export.

2. Logical architecture

The UI never calls a provider or writes SQL. The analytics layer never imports Streamlit. External response shapes terminate inside source adapters.

4. Data model

Use integers for internal primary keys and preserve provider identifiers as unique business keys. Store dates as ISO text in SQLite and convert to typed dates at repository boundaries.

The benchmark seed data contains exactly five version 1 identities: Nifty 50 TRI, Nifty Next 50 TRI, Nifty 500 TRI, Nifty Midcap 150 TRI, and Nifty Smallcap 250 TRI.

5. Data and analytics pipelines

5.1 Refresh pipeline

  1. Acquire. Provider adapter downloads data with timeout and bounded retries into a temporary location.
  2. Fingerprint. Calculate checksum and register an immutable source snapshot.
  3. Parse. Convert source-specific fields into canonical staging records without changing the current database.
  4. Validate. Check schema, types, uniqueness, domain bounds, coverage, freshness, and unexpected row-count changes.
  5. Reconcile. Compare conflicting values and apply explicit source precedence while retaining conflict records.
  6. Commit. Upsert normalized records in one transaction only after all blocking validations pass.
  7. Derive. Update monthly series and invalidate only analytics affected by changed inputs.
  8. Publish health. Mark the run successful and expose counts, dates, warnings, and versions to the UI.

5.2 Full rebuild pipeline

  1. Resolve eligible schemes through the versioned classifier.
  2. Build first-available-on-or-after-the-1st monthly series.
  3. Precompute trailing observations for supported horizons.
  4. Precompute fund and benchmark rolling observations for all six presets and both modes.
  5. Build common-period keys and summary statistics.
  6. Calculate independent and benchmark-relative risk metrics.
  7. Calculate category percentiles and multi-period consistency.
  8. Run post-build integrity checks before replacing the active analytics version.

5.3 Incremental strategy

Daily refresh should insert only new NAV/index dates, rebuild the affected monthly point if necessary, append newly completed rolling windows, refresh trailing values, and recompute summaries that include the changed endpoint. A full rebuild remains the correctness fallback.

6. Core algorithms

6.1 Monthly observation selection

for each calendar month M in available history:
    candidates = observations where date >= first_day(M)
                              and date < first_day(M + 1 month)
    if candidates is empty:
        mark M as missing
    else:
        choose candidate with minimum date
        store requested_month=M and actual_date=candidate.date

A missing month must remain missing. Do not silently use the previous month's last NAV because that changes the agreed investment convention.

6.2 Rolling SIP XIRR

inputs: monthly series, start month S, duration M months
cash_flows = []
units = 0

for offset in 0 .. M-1:
    point = monthly_point(S + offset)
    require point exists
    contribution = 1.0
    units += contribution / point.value
    cash_flows.append((point.actual_date, -contribution))

terminal = monthly_point(S + M)
require terminal exists
cash_flows.append((terminal.actual_date, units * terminal.value))

return validated_xirr(cash_flows)

Use the same method for a benchmark TRI. A nominal contribution of 1 is sufficient because uniform cash-flow scaling does not change XIRR.

6.3 Rolling lump-sum CAGR

start = monthly_point(S)
end   = monthly_point(S + M)
elapsed_years = (end.actual_date - start.actual_date).days / 365.2425
return (end.value / start.value) ** (1 / elapsed_years) - 1

6.4 Common-period comparison

for each selected fund and mode:
    produce keyed observations by (preset, start_month, valuation_month)

common_keys = intersection(all selected series keys)
filter every series to common_keys
calculate chart and statistics only from filtered series
report both common count and each fund's full available count

6.5 Risk and benchmark metrics

  • Convert aligned monthly levels to simple returns.
  • Convert annual 91-day T-bill yield to a monthly effective rate using a documented convention.
  • Sharpe: mean monthly excess return divided by standard deviation of monthly excess returns, multiplied by square root of 12.
  • Sortino: mean monthly excess return divided by downside deviation of negative excess returns, multiplied by square root of 12.
  • Tracking error: standard deviation of monthly fund-minus-benchmark return, multiplied by square root of 12.
  • Information ratio: annualized mean active return divided by annualized tracking error.
  • Capture: annualize geometrically compounded returns over benchmark-up or benchmark-down months, then take fund divided by benchmark.

6.6 Drawdown

wealth = value / first_value
running_peak = cumulative_max(wealth)
drawdown = wealth / running_peak - 1

maximum_drawdown = minimum(drawdown)
peak_date = date of running peak preceding the trough
trough_date = date of maximum_drawdown
recovery_date = first later date where wealth >= prior peak, else null

7.1 View-model rule

Application services return display-ready view models containing labels, units, availability reasons, source dates, and values. UI formatting functions may change presentation but may not recalculate finance metrics.

7.2 Chart conventions

  • Fund identity owns color; calculation mode owns line style.
  • SIP is solid and lump sum is dashed.
  • Benchmark uses a neutral dark line and category median uses a muted dotted line.
  • Returns are displayed as percentages but retained as decimals internally.
  • Every chart has a companion table or export.
  • When "both" mode with five funds becomes crowded, the legend permits isolating series without removing them from common-period calculations.

8. Error, cache, and state design

8.1 Structured domain outcomes

CodeMeaningUser behavior
INSUFFICIENT_HISTORYRequested trailing or rolling period cannot be completed.Show unavailable period; do not plot or rank it.
MISSING_MONTHNo valid observation exists in a required month.Exclude affected window and show count.
BENCHMARK_DISABLEDFund class is not eligible for the Indian benchmark selector.Hide relative metrics and explain why.
BENCHMARK_GAPSelected TRI lacks aligned data.Keep independent metrics; disable affected relative output.
XIRR_NO_SOLUTIONCash-flow sequence is invalid or solver cannot converge.Flag observation; never coerce to zero.
STALE_DATASource age exceeds the configured threshold.Permit cached analysis with prominent date warning.

8.2 Cache keys

Cache keys include dataset version, calculation version, scheme or benchmark ID, mode, preset, period key, and relevant configuration version. Streamlit's in-process cache may accelerate reads, but SQLite remains the durable derived-result cache.

8.3 Session versus persistent state

  • Session: current filters, selected funds, chart toggles, temporary date range.
  • Persistent: shortlist, optional notes, last successful refresh, dataset versions, methodology configuration.
  • Never persist stale UI objects or data frames in a way that bypasses version checks.

9. Key design decisions

ADR-01

Streamlit modular monolith

Use Streamlit rather than a separate JavaScript frontend and REST backend.

Trade-off: faster student delivery and less infrastructure; reduced frontend customization. Domain isolation preserves a future migration path.

ADR-02

Precompute rolling observations

Persist observations for six known presets and both modes after data refresh.

Trade-off: longer rebuild and more storage; much faster interactive ranking and consistent shared results.

ADR-03

SQLite as source of truth

Keep normalized and derived records in one local relational database; retain raw files separately.

Trade-off: simpler operations and joins; not intended for concurrent multi-user workload.

ADR-04

Provider abstraction and retained snapshots

Every external dataset is accessed through a port and every accepted input is fingerprinted.

Trade-off: more initial code; protects the project from provider changes and makes results auditable.

ADR-05

No universal score

Expose sortable metrics, filters, category percentiles, and transparent shortlist reasons.

Trade-off: requires more user judgment; avoids false precision and hidden weighting.

ADR-06

Current-category interpretation

Version 1 uses the fund's current normalized category for ranking and discloses that historical category changes are not reconstructed.

Trade-off: feasible free implementation; historical peer groups may not perfectly match old mandates.
