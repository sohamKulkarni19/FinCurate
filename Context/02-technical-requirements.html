1. Engineering goals

Correct before clever

Every published number must be reproducible from retained inputs, explicit conventions, and a versioned calculation method.

Local first

The complete application, database, cache, shortlist, and exports run on one laptop without authentication or cloud infrastructure.

Replaceable sources

External NAV, benchmark, and risk-free providers are isolated behind adapters and never called directly from analytics or UI code.

Teachably modular

A CSE student can understand, test, and modify one layer without learning a distributed architecture.

Architecture constraintUse a modular monolith. A separate API server, job queue, container cluster, user service, or cloud database is not justified for version 1.

2.1 Supported workstation

  • Windows 11, current macOS, or a mainstream Linux distribution.
  • Four CPU cores, 8 GB RAM, and 2 GB free disk space minimum; 16 GB RAM recommended for full-universe recomputation.
  • A modern Chromium, Firefox, or Safari browser.
  • Internet access required only for dataset refresh; analysis must work from local data.

2.2 Dependency policy

TR-101

Reproducible environment

Must

A clean workstation shall create the environment and run tests using documented commands. Application dependencies shall be pinned by a lock file; development tools shall be separated from runtime dependencies.

TR-102

No runtime CDN dependency

Must

Core application operation shall not depend on externally hosted JavaScript, fonts, or styles. Package assets may be served locally by the application.

3.2 Data contracts

TR-201

Immutable raw snapshots

Must

Each refresh shall retain the unmodified source response or file with retrieval timestamp, source URL or identifier, checksum, and adapter version. Derived tables shall be rebuildable from retained snapshots.

TR-202

Canonical types

Must

Dates shall be ISO calendar dates without implicit timezone conversion. NAV, index value, and yields shall be parsed as decimal-compatible numeric values and rejected when non-positive or malformed.

TR-203

Idempotent ingestion

Must

Reprocessing the same source snapshot shall not create duplicate schemes, NAVs, benchmark values, or refresh events.

TR-204

Source precedence

Must

When a validated AMFI record conflicts with the convenience API for the same scheme and date, the conflict shall be logged and the configured authoritative source shall win. Existing values shall never change silently.

3.3 Universe classification

TR-205

Direct Growth classifier

Must

Eligibility shall be produced by one deterministic, tested classifier using structured metadata first and normalized name rules second. Records with ambiguous plan or option shall be quarantined, not guessed into the universe.

TR-206

Active open-ended status

Must

Active status shall combine source status with freshness checks. The staleness threshold shall be configuration, visible in methodology, and tested against holiday periods.

TR-207

Category normalization

Must

Map source labels to a versioned application taxonomy while retaining the raw label. Unmapped categories shall not enter category rankings.

3.4 Validation and health

  • Uniqueness: at most one NAV per scheme per date and one index value per benchmark per date.
  • Ordering: dates strictly increase within every time series after deduplication.
  • Domain: NAV and index values are positive; annual yields lie within a configurable plausible range.
  • Coverage: every eligible scheme reports inception, latest date, row count, missing-month count, and history span.
  • Continuity: large one-day changes are flagged for review, not automatically corrected.
  • Monthly selection: every derived first-of-month point retains the requested month and actual source date.
  • Lineage: every calculated observation can identify its source snapshot and calculation version.

4. Analytics and numerical requirements

4.1 Calculation engine

TR-301

Pure calculation functions

Must

Return calculations shall accept explicit typed inputs and return results without database, network, UI, or global-state access. This is required for deterministic unit testing.

TR-302

Date-safe month handling

Must

Calendar-month arithmetic shall use a date-aware offset, not fixed 30-day intervals. The requested month and actual NAV date shall both be preserved.

TR-303

XIRR convergence

Must

The XIRR wrapper shall validate sign changes, finite cash flows, unique dates, and solver output. Non-convergence shall produce a structured error and shall never be replaced with zero.

TR-304

Numerical precision

Must

Intermediate calculations shall retain at least IEEE 64-bit precision. Values shall be rounded only for display or export. Percentage-point differences shall be computed before display rounding.

TR-305

Aligned comparisons

Must

Fund, peer, benchmark, and risk-free series shall be inner-joined on explicit month/date keys before relative metrics are computed. The resulting observation count shall be retained.

4.2 Statistical conventions

Metric familyRequired frequency and convention
Rolling outcomesMonthly commencement frequency; six locked durations; actual-day annualization; population descriptive statistics over included observations.
Risk ratiosMonth-end or first-of-month aligned monthly returns; annualization by square root of 12 where applicable; minimum observation threshold configured and shown.
CapturePartition aligned months by benchmark return above or below zero. Use geometrically compounded conditional fund and benchmark returns; show underlying up/down month counts.
DrawdownCompute from the most granular validated NAV series available; use normalized wealth index and running peak.
Category percentileUse only eligible funds with the same period, duration, and sufficient history. State percentile direction for metrics where lower is better.
Return distributionsUse mutually exclusive, collectively exhaustive bands with explicit lower/upper boundary rules.

4.3 Cache and reproducibility

TR-306

Versioned derived results

Must

Every precomputed result shall include dataset version, calculation version, preset, observation dates, and common-period key. A calculation-code version change shall invalidate incompatible cached results.

TR-307

Rebuild command

Must

A documented command shall rebuild monthly NAV selections, trailing results, rolling results, risk metrics, and category summaries from normalized data.

5.2 Reliability and recoverability

NFR-08

Atomic refresh

Must

A failed download, parse, validation, or database transaction shall leave the last known-good dataset queryable.

NFR-09

Backup

Must

Before schema migration or full replacement, create a timestamped local database backup and document restoration.

NFR-10

Offline operation

Must

If refresh sources are unavailable, the application shall start with cached data, show its age, and disable only refresh-dependent actions.

5.3 Usability and accessibility

  • Target a 1366 x 768 laptop as the minimum primary layout; remain usable at 768 px width.
  • Use color plus line style, symbol, or label; never encode meaning using color alone.
  • Charts require titles, axis labels, units, legend, hover details, and a tabular alternative.
  • Keyboard navigation and visible focus must work for primary controls.
  • Plain-language empty, loading, stale, and error states are required.
  • Numbers use Indian grouping where currency is shown, but data exports remain machine-friendly.

5.4 Privacy and local security

  • Bind the development server to localhost by default, not all network interfaces.
  • Collect no personal financial account, folio, tax, email, or identity data.
  • Keep shortlist and settings in local storage or SQLite.
  • Do not commit database files, raw large datasets, logs with tokens, or local environment files to source control.
  • Apply request timeouts, bounded retries, and response-size checks to external data calls.
  • Use no hard-coded credentials. Version 1 should require none for its preferred sources.

5.5 Maintainability

  • Public functions and domain types require type hints and concise docstrings.
  • UI pages may call application services, not repositories or provider clients directly.
  • All source-specific field names shall terminate at the adapter boundary.
  • Calculation formulas and business constants shall live in named modules, not UI callbacks.
  • Database schema changes require numbered migrations.
  • Every release shall record methodology version and data-source versions.

TR-401

Numerical tolerance

Must

Golden tests shall define tolerances before comparison. Proposed default: return and ratio outputs within 0.01 percentage point of independently verified values, unless source rounding makes a wider documented tolerance necessary.

TR-402

Coverage policy

Must

Calculation and classification modules require at least 95% statement coverage and full branch coverage of declared edge cases. Overall project coverage shall not fall below 85%.

TR-403

Quality gate

Must

Formatting, linting, type checking where enabled, tests, and database migration checks shall pass before a release tag.

7. Local operations

7.1 Required commands

# First setup
project setup

# Refresh external datasets without publishing partial data
project data refresh

# Validate retained and normalized data
project data validate

# Rebuild all derived analytics
project analytics rebuild

# Start the localhost application
project app run

# Run automated quality checks
project test

The final command names may use a Makefile, task runner, or Python CLI. The requirement is one documented entry point per operation.

7.2 Logging

TR-501

Structured operation log

Must

Refresh and rebuild operations shall log run ID, start/end time, input versions, row counts, validation outcomes, warnings, and failure reason. Logs shall exclude secrets and remain locally bounded by rotation.

TR-502

Visible data health

Must

The application shall show last successful refresh, last validation, last analytics rebuild, known warnings, and database version.

7.3 Schema and methodology changes

  • Schema migrations are forward-only scripts with tested backup restoration.
  • Formula changes increment the calculation version and invalidate dependent caches.
  • Category-map changes retain their effective date and previous version.
  • Benchmark file replacements retain checksum and provenance.
